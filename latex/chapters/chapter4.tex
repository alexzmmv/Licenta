\chapter{Evaluation}
\label{chap:evaluation}

\section{Evaluation Setup}

\subsection{Datasets}

Two standard datasets cover different aspects of embedding quality:

\begin{itemize}
  \item \textbf{STS-B} \cite{cer2017semeval} (Semantic Textual Similarity Benchmark): 1500 sentence pairs scored by human annotators on a 0--5 similarity scale. Spearman rank correlation between model-predicted cosine similarities and the gold scores measures how well a model captures semantic meaning.
  \item \textbf{TwentyNewsgroupsClustering}: 1000 sentences drawn from 20 newsgroup topic categories. Ground-truth topic labels allow direct measurement of clustering quality.
\end{itemize}

Domain validation uses 100 manually labelled journal entries written during the testing period, annotated with ground-truth topic groupings. This set tests whether behaviour on standard benchmarks carries over to the actual application domain.

\subsection{Metrics}

Embedding quality is measured with Spearman rank correlation ($r_s$) on STS-B. Clustering quality uses:

\begin{itemize}
  \item \textbf{V-measure} \cite{rosenberg2007vmeasure}: harmonic mean of homogeneity and completeness. A cluster has high homogeneity if it contains entries from only one ground-truth class; high completeness if all members of a class land in the same cluster.
  \item \textbf{ARI} (Adjusted Rand Index) \cite{hubert1985comparing}: agreement between predicted clusters and ground-truth labels, corrected for chance. Values range from 0 (random) to 1 (perfect).
  \item \textbf{Noise fraction}: the share of points DBSCAN marks as noise and leaves unclustered. High noise can mean over-strict parameters or genuinely sparse embeddings.
\end{itemize}

\subsection{Hardware}

All Python benchmarks run on an Apple M-series processor using the MPS backend (PyTorch). Apple NLEmbedding embeddings are generated by a standalone Swift script (\texttt{embed\_apple\_nlp.swift}) running on the same machine via \texttt{swift} command-line, then consumed by the Python pipeline as pre-computed JSON. This approach is necessary because \texttt{NLEmbedding} is a macOS/iOS SDK API not accessible from Python.

\section{Embedding Models}

Three strategies are implemented in GJournal behind the \texttt{EmbeddingService} protocol:

\begin{itemize}
  \item \textbf{Apple NLEmbedding}: the sentence embedding provided by the iOS%
\newline \texttt{NaturalLanguage} framework,%
\newline via \texttt{NLEmbedding.sentenceEmbedding(for:~.english)}.%
\newline It produces 512-dimensional vectors with no additional bundle cost; the model weights are part of the operating system. Because this API is only callable from Swift, a standalone macOS Swift script (\texttt{embed\_apple\_nlp.swift}) was written to embed all benchmark sentences and export them to JSON for the Python evaluation pipeline. This approach allowed Apple NLEmbedding to participate in all three evaluation steps under the same metrics and DBSCAN configuration used for the other models.
  \item \textbf{all-MiniLM-L6-v2} \cite{reimers2019sentencebert}: a 6-layer MiniLM model producing 384-dimensional mean-pooled embeddings. Converted to a 45\,MB Core ML package. This model is the default in GJournal.
  \item \textbf{nomic-embed-text-v1.5} \cite{nussbaum2024nomic}: a 768-dimensional model trained with Matryoshka Representation Learning (Section~\ref{sec:mrl}). Converted to a 274\,MB Core ML package. The model is instruction-tuned: it was trained with task-specific text prefixes that condition the embedding space for a stated downstream task. Supported prefixes include:
  \begin{itemize}
    \item \texttt{"search\_query: "}
    \item \texttt{"search\_document: "}
    \item \texttt{"classification: "}
    \item \texttt{"clustering: "}
  \end{itemize}
  GJournal prepends \texttt{"clustering: "} to every input so the model produces embeddings whose geometry is optimised for grouping similar texts, rather than a generic representation. The GJournal default configuration uses 256-dimensional MRL truncation.
\end{itemize}

\section{Matryoshka Representation Learning}
\label{sec:mrl}

Standard embedding models fix output dimensionality at training time. Reducing it after training typically requires retraining from scratch or post-hoc compression, both of which degrade quality. Matryoshka Representation Learning \cite{kusupati2022matryoshka} avoids this by training the model with a nested loss: the full $d$-dimensional output optimises a similarity objective, and simultaneously each prefix sub-vector of length $d' < d$ optimises the same objective independently. The result is that any prefix of the output vector is itself a competitive embedding.

For GJournal, the practical consequence is that the 274\,MB nomic model can produce embeddings at \{64, 128, 256, 512, 768\} dimensions by truncating its output after inference. No additional models or fine-tuning are needed. Table~\ref{tab:mrl_tradeoff} shows how Spearman correlation, silhouette score \cite{rousseeuw1987silhouettes}, and latency change across dimensions.

\begin{table}[h]
\centering
\caption{Nomic-v1.5 MRL dimension trade-off on STS-B (clustering prefix, Python/MPS benchmark)}
\label{tab:mrl_tradeoff}
\begin{tabular}{|r|c|c|c|c|}
\hline
\textbf{Dim} & \textbf{Spearman $r_s$} & \textbf{Silhouette} & \textbf{$\varepsilon$ (MRL-scaled)} & \textbf{Latency (ms)} \\
\hline
 64 & 0.8408 & 0.1193 & 0.0866 & 20.7 \\
128 & 0.8521 & 0.1122 & 0.1225 & 20.4 \\
256 & 0.8571 & 0.1004 & 0.1732 & 20.3 \\
512 & 0.8584 & 0.1097 & 0.2449 & 20.2 \\
768 & 0.8596 & 0.1158 & 0.3000 & 20.2 \\
\hline
\end{tabular}
\end{table}

Latency is flat across all dimensions in the Python benchmark: inference takes approximately 20\,ms on Apple MPS regardless of output size because the transformer forward pass dominates and the output slice is cheap. On-device Core ML numbers are reported in Section~\ref{sec:efficiency}. The Spearman gap from 128-dim (0.8521) to full 768-dim (0.8596) is 0.0075, so the accuracy cost of $6\times$ compression is small. Quality drops more noticeably below 128 dimensions: going from 128 to 64 loses 0.0113 Spearman.

The scaled $\varepsilon$ column shows the DBSCAN neighbourhood radius after MRL adjustment: $\varepsilon_d = \varepsilon_{768} \cdot \sqrt{d / 768}$. This compensates because cosine distances in lower-dimensional spaces tend to be smaller on average, which would otherwise cause DBSCAN to over-cluster at short dimensions.

\section{Algorithm Comparison}

Four DBSCAN variants were compared on TwentyNewsgroups using Nomic-768 embeddings. DBCV (Density-Based Clustering Validation) \cite{moulavi2014dbcv} is included as an additional quality measure suited to density-based methods. Table~\ref{tab:algorithm_comparison} shows the results.

\begin{table}[h]
\centering
\caption{Algorithm comparison on TwentyNewsgroupsClustering (Nomic-768, 1000 sentences)}
\label{tab:algorithm_comparison}
\begin{tabular}{|l|c|c|c|c|c|c|}
\hline
\textbf{Algorithm} & \textbf{V-m} & \textbf{ARI} & \textbf{Homog} & \textbf{Compl} & \textbf{Noise\%} & \textbf{Clusters} \\
\hline
Vanilla DBSCAN   & 0.009          & 0.000          & 0.004          & 0.496 &  1.8\% &  2 \\
Classic Adaptive & 0.477          & 0.121          & 0.322          & 0.924 & 40.4\% &  5 \\
MRL-Adapted      & 0.183          & 0.017          & 0.106          & 0.685 & 27.2\% &  5 \\
HDBSCAN \cite{campello2013hdbscan} & \textbf{0.737} & \textbf{0.421} & \textbf{0.832} & 0.661 & 63.3\% & 52 \\
\hline
\end{tabular}
\end{table}

Fixed-epsilon Vanilla DBSCAN collapses the corpus into two clusters regardless of topic, giving near-zero V-measure. Classic Adaptive, which calibrates epsilon per corpus, raises V-measure to 0.477. The MRL-Adapted variant scales epsilon by $\sqrt{d/768}$; on TwentyNewsgroups it underperforms Classic Adaptive (V-measure 0.183) because the uniform topic distribution does not benefit from the correction designed for short journal entries.

HDBSCAN achieves the best purity (V-measure 0.737, ARI 0.421) but produces 52 clusters on 1000 sentences. In a journaling app with 20 to 50 entries the equivalent behaviour would create a cluster per entry or small group, making the insight view uninformative. Classic Adaptive DBSCAN is the practical choice for this application.

On actual journal text the gap between MiniLM and Nomic widens. MiniLM V-measure is 0.662 versus 0.511 for Nomic-256, a difference of 15 percentage points. The combination of low completeness (0.711) and high noise makes it unsuitable as the primary embedding model for a journaling application, though its zero bundle cost remains an advantage when storage is the binding constraint.

MiniLM has the lowest warm latency at 5.4\,ms, about six times faster than either Nomic variant (32\,ms) and twice as fast as Apple NLEmbedding (10\,ms). Nomic-256d and Nomic-768d take the same time: 32.2\,ms versus 31.9\,ms, a 0.3\,ms gap within measurement noise. MRL truncation adds no inference overhead, which confirms the result from the Python benchmark in Section~\ref{sec:mrl}: the transformer forward pass dominates and the output slice is cheap.

Cold starts are significant. MiniLM takes 1.9\,s on its first call; Nomic takes 3.6\,s. Both are handled by lazy loading: models load on the first entry save, not at app launch, so the user does not wait at startup. Apple NLEmbedding has a 704\,ms cold start despite no bundle file; this is the cost of the first call into the \texttt{NLEmbedding} framework.

The three Core ML bundles total 418\,MB (MiniLM 45\,MB + Nomic 274\,MB + emotion 99\,MB). GJournal ships all three so the user can switch models without a download. Apple NLEmbedding adds nothing to the bundle because its weights are part of iOS.

\section{Discussion}

MiniLM outperforms all other models on clustering metrics across both the standard benchmark and the journal domain. Its 384-dimensional output, trained for semantic similarity tasks, is better calibrated for cosine-distance DBSCAN on short texts. Nomic's MRL support does not close that gap.

Apple NLEmbedding scores 0.717 Spearman on STS-B, usable for rough semantic similarity but 0.15 below MiniLM. Its clustering performance is much weaker: V-measure 0.020 on TwentyNewsgroups and 0.459 on journal entries. The poor clustering result reflects the API's design: \texttt{NLEmbedding.sentenceEmbedding} is a general-purpose on-device model trained across many language tasks, not for dense retrieval or clustering. Its advantage is zero bundle cost; the weights ship with the OS. That makes it a reasonable fallback when storage is the binding constraint, but not the primary embedding strategy.

MRL truncation reduces storage without affecting inference time. At 256 dimensions each embedding occupies $256 \times 4 = 1{,}024$ bytes versus $768 \times 4 = 3{,}072$ bytes at full size; over 1000 journal entries that is roughly 2\,MB saved in the SwiftData store. The Spearman cost on the MRL benchmark (Table~\ref{tab:mrl_tradeoff}) is 0.0025, a drop of 0.29\%. The on-device benchmark (Table~\ref{tab:efficiency}) confirms that Core ML inference time is flat at approximately 32\,ms regardless of output dimension, so there is no speed reason to choose 256d over 768d. The only benefit is storage.

The practical outcome for GJournal is that MiniLM is the default: best clustering quality, smallest dedicated bundle at 45\,MB, fastest warm inference at 5.4\,ms per entry, no prefix requirement. Nomic at 256 dimensions is available as a user-selectable option. Apple NLEmbedding remains available as a zero-cost fallback for devices where storage is the binding constraint.
